# Project Lead

[English](README.md) | 简体中文

一个用于协调多模块项目、自动判断 Spark 或 Terra 执行模型、让 Luna 承担有边界的只读信息整理、自动选择合适配套 Skill，并避免普通任务陷入无效审查循环的 Codex Skill。

## 核心变化

Project Lead 现在只遵守一个原则：**根据真实风险使用最少但足够的流程**。项目进度看的是用户能否得到可用结果，而不是创建了多少任务、做了多少轮审查或输出了多长的技术报告。

总控负责范围、任务归属、阻塞、验收和汇报；执行线程负责项目产物和实质执行。普通任务由一个明确 owner 快速推进，高风险任务保留独立门禁。

## 总控审批权与执行边界

在已经批准的项目目标内，总控自行批准正常派发、本地可逆准备、针对性检查、规定的独立审查和范围内返修。Elevated 审查本身不需要用户批准：内容风险决定审查强度，拟执行动作和缺少的权限才决定是否询问用户。只有真实的产品或安全策略分叉、新权限或密钥、不可逆或破坏性操作、外部副作用、付费、部署或发布才交给用户；真正只能由用户点击的平台批准卡仍会立即转达。

总控只承担接管、路由、无代码的跨模块决策、验收、汇报和快速只读抽查。计划、设计、源码、测试、复杂调试和长验证都属于执行任务，不能拆成多个“小步骤”留在总控。旧批准阻塞绑定一个具体目标、候选、动作和权限缺口；身份或需求变化后立即失效。

Elevated 风险只会提高独立审查强度，不会自动创建一轮总体架构。只有出现真实的跨客户端或跨服务边界、未解决的共享契约或重大返工风险，才进入总体架构阶段。

## 可见的执行任务

正式实施、独立审查和长验证必须通过 `create_thread` 创建为有明确标题、侧边栏可见的独立 Codex 任务，不能用内部子智能体替代。这样用户可以在左侧找到任务、查看完整过程，并处理相应的批准卡。若 `create_thread` 不可用，Project Lead 报告 `blocked_on_visibility`，不会把工作说成已派发。内部子智能体只可做短时只读辅助，不能拥有可变范围、等待用户批准、审查、验收或结项正式任务。

## 自动选择与搜索 Skill

**你只需要描述目标，不需要记住 Skill 名称。** 在接收项目以及进入每个新阶段时，Project Lead 会：

- 有明确触发条件时，自动选择并调用最多一个已经安装的相关 Skill；
- 普通且范围明确的工作选择 `none`，不会为了“保险”堆叠一批 Skill；
- 只有确实缺少必要的专业验收能力时，才进行一次保护隐私的只读公开搜索；
- 最多推荐三个候选，说明对当前项目的作用和风险，并且任何安装前都会先征得你的同意。

例如，涉及 Apple 手势和动效时可以选择 `apple-design`，遇到真实模块边界问题时可以选择 `codebase-design`，验证可运行的网页流程时可以选择 `webapp-testing`。搜索到的候选说明始终按不可信信息处理，不会在搜索阶段执行或自动安装。

## 自动选择执行模型

用户每个项目只授权一次自动路由。每个新目标都会根据当前边界明确的子任务本身——动作、不确定性、耦合、后果、检查，以及派发工具实际支持的组合——同时选择模型和推理档位，绝不继承上一个目标的路由，也不会继承父项目、审查通道或上一个任务的档位。

- Spark high 处理路径唯一、可逆且有确定检查的任务；Spark xhigh 还必须有一个说得清的本地推理难点，不能只因为它属于低风险任务就升档。
- Terra high 处理一个契约和检查已知的实现、调试或设计问题；存在多个合理原因或方案，或多项约束无法拆开时才用 xhigh；只有一个目标真实运行多个互不争抢文件的大型独立工作流时才用 Ultra。
- Luna 默认 medium 做只读提取；多来源密集证据可用 high；只有难解的证据冲突才用 xhigh。无论档位多高，都不能写代码、审查或验收。
- 执行路由不会削弱独立审查：标准审查仍由独立 Terra 完成，高风险审查仍由独立 Sol 完成。

选择 xhigh 或 Ultra 前，总控会做一次总控内部静默判断：说明低一档最可能造成的具体失败风险。这个判断不会调用工具、新建任务、调用 Luna 或并行比较模型；如果说不出当前任务特有的风险，就根据当前证据重新选择，不能因为信息不全或父项目复杂而直接升档。

每次派发前会告知任务、模型、档位和实际速度，并附上一句当前任务的选择理由；只发一行，不会等待批准，这是通知而不是请示。速度默认显示普通，只有用户已明确要求该目标使用 Fast 时才显示 Fast。如果额度回退或实际路由核验改变了选择，总控会先发更正通知再重新派发。

通过 `create_thread` 创建的正式执行任务从空白上下文开始。内部辅助和审查任务只获得无历史或有限历史，不能继承完整历史。如果派发工具能原子返回实际路由，就在开工前核对；否则先建立一个禁止读取、修改项目或调用工具的握手任务，确认模型和档位后才发送正式任务。无法观察实际路由时报告 `blocked_on_routing`，不能猜测。

没有模型和档位字段的普通跟进不能原地切换；当前回合结束或中止后，再把同一逻辑范围交接给唯一一个路由正确的任务，绝不产生两个并发负责人。Spark 回退 Terra 时，只等待同一目标或逻辑范围里的 Spark 回合；无关范围仍可并行推进。

## 下发任务默认使用普通速度

Fast 速度不等于低风险通道。总控本身可以保留用户当前设置的速度，但该设置不会授权给下发任务。每个新执行任务默认使用 Standard/普通速度，后续继续执行也保持普通速度；Project Lead 不会主动询问是否使用 Fast。只有用户主动明确要求当前子任务使用 Fast 时才启用，目标结束后立即失效。

派发接口没有速度字段时，不传入任何 Fast/priority 覆盖，直接使用平台的 Standard/普通默认值；缺少字段不会阻塞普通派发。如果之后出现子任务意外使用 Fast/priority 的真实证据，总控停止继续派发并立即说明。

## Luna 只读信息助理

当大量或重复的证据会明显占用总控上下文或额度时，Project Lead 只保留一个项目级 `gpt-5.6-luna` 逻辑范围，通常使用 medium；需要换档时也遵守单一负责人交接规则。它负责汇总长任务报告、日志和测试输出，提取进度、阻塞、待批准事项和终态，合并重复状态，并起草通俗进度。

只有几行内容或普通状态更新不会调用 Luna。它的结果只是带来源的辅助信息，总控采取行动前仍要核对原始证据。Luna 不会写代码、选择模型、审查、验收或宣布完成，也不能代替必要验证。

## 事件驱动的完成回传

执行任务接受派发后，Project Lead 使用 `wait_threads` 保持总控回合，直到所有承诺等待的任务完成或需要处理。等待超时只会续接事件等待，不会触发轮询、重复读取或调用 Luna。一个任务结束时，总控先在过程中转达，再继续等待其他任务。

只有需要用户输入、用户明确停止等待或事件等待工具不可用时，总控才能提前结束。工具不可用时必须说明无法保证自动回传。Luna 和 30 分钟规则都不能唤醒空闲总控。

## 风险分级审查

| 模式 | 适用情况 | 审查方式 |
| --- | --- | --- |
| 低风险通道——默认 | 文案、样式、测试、本地修复、小型可逆行为、既定接口下的孤立改动 | 不创建独立审查线程。总控核对真实 diff、工作区和针对性检查后直接验收。 |
| 标准模式 | 单一模块内有实际逻辑的多文件改动，或既定契约下的有限集成 | 完整候选稳定后集中做一次 `gpt-5.6-terra high` 审查；最多再做一次增量修复复审。Minor 不触发退回。 |
| 高风险模式 | 鉴权、授权、密钥、隐私或受监管个人数据、加密协议或安全合规、支付、破坏性操作、数据丢失或所有权、迁移、并发与恢复、共享契约、跨模块集成、部署、发布或总体架构 | 一个稳定候选使用独立 `gpt-5.6-sol xhigh` 审查。确实不可逆的前置架构决定可以在实现前单独审查一次。 |

同一目标在两次退回后不再重复相同的增量审查循环。Standard 第二次退回后，总控自行派发一次范围内根因修复，再根据执行线程的新证据和一次聚焦抽查逐项关闭 finding；无法证明修好的继续保持 `RETURN`。Elevated 第二次退回后，总控自动派发一次范围内根因修复和一次最终独立收口审查；绝不发起第四轮，仍被退回就保持 `blocked_on_quality` 和未完成状态。

## 工作方式

1. 检查当前代码仓库和活跃任务。
2. 区分当前可用结果与以后可做的优化。
3. 每个可变范围只保留一个负责人，修复继续复用原任务。
4. 根据具体风险选择低风险、标准或高风险模式。
5. 只运行改动范围和项目规则真正要求的检查。
6. 用用户能看懂的语言汇报进度。

委派的低风险任务只有在全部白名单条件成立时才使用 Spark；项目产物、主要实现、复杂调试和长时间验证都留在执行线程。

信息不足不会自动升级成总体架构任务或用户问题。总控先自行检查或派发取证，只有用户独占的产品事实或新权限才询问。只有真实的跨客户端/服务边界、未解决的共享契约或重大返工风险，才进入总体架构阶段。

## 简明反馈

默认只给用户四行：

```text
已完成：<用户能理解的结果>
当前结果：<能否使用或验证>
阻塞：无 | <需要用户处理的唯一事项>
下一步：<一个最有价值的动作>
```

除派发前必须显示的模型与档位通知外，Base/Head、SHA、审查编号和内部台账默认隐藏；只有用户主动询问，或它们能解释真实阻塞时才展示。

被总控验收的执行任务会收到一次结项回执：

```text
【总控结项回执｜非新任务，无需回复】
当前任务：<已接受的任务目标>
当前状态：已完成，等待下一步指令。
```

## 协调与批准提醒

- 一个工作区或可变范围只允许一个负责人。
- 独立模块可以并行，共享文件、迁移和共享契约必须串行。
- 派发成功不等于任务完成；总控必须读取终态报告并核验证据。
- 只有真正越过审批边界的请求才通知用户，并说明任务、动作、风险和操作位置。总控不会把普通审查或本地工作包装成文字审批，也不会猜测平台批准卡正文。
- 连续 30 分钟没有实质进展时，只允许一次只读快照和一次 Luna 状态询问；不创建 heartbeat、cron 或轮询。

## 配套 Skill 与能力发现

每个阶段最多选择一个真正需要的设计或探索类 Skill；普通工作不额外启用任何 Skill。

缺失能力查找已经内置，而且只读，不调用 `find-skills`。只有确实缺少专业验收方法时才搜索；搜索词会脱敏，候选内容按不可信信息处理，最多推荐三个。发现过程不会自动安装，也不会阻塞无关工作。

候选绑定、原子安装、失败回滚和崩溃恢复细节放在[安装安全参考](skills/project-lead/references/skill-installation-safety.md)中，只有用户批准精确候选后才读取。这样普通项目不会承受安装协议的上下文成本，同时保留原有安全边界。

## 安装

为 Codex 全局安装：

```bash
npx skills add yousef555khg-beep/project-lead@project-lead -g -a codex
```

开始总控对话时输入：

```text
使用 project-lead 管理这个项目。
```

## 配套 Skills

- 每个模式验收前使用 `verification-before-completion`。
- 只有标准和高风险审查节点使用 `requesting-code-review`。
- `prototype`、`codebase-design`、`apple-design`、`webapp-testing` 只在对应触发条件确实存在时使用。
